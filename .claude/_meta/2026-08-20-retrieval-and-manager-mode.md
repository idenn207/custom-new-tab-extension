### 목표 갱신의 정체 — 새 목표가 아니라 두 번째 상태

사용자 진술: "평소에는 리마인드 역할을 하면서 단순히 지나치는 화면이지만, 사용하는 순간부터는 내 프로젝트들을 관리하는 매니저가 된다."

이것이 전제 7·8과 충돌하는 것처럼 보이지만 **충돌하지 않는다.** `PRODUCT.md`는 "대부분은 1초 안에 떠난다"고 썼지 "항상 1초 안에 떠난다"고 쓰지 않았다. 사용자의 진술은 그 1초를 부정하지 않고 **드물게 머무는 경우를 추가**한다.

즉 이것은 하나의 화면에 있는 **두 개의 상태**다.

| | Ambient (지나침) | Engaged (머무름) |
|---|---|---|
| 빈도 | 방문의 대부분 | 드묾 |
| 진입 | 새 탭을 여는 것 자체 | **명시적 행동**(단축키·클릭) |
| 주인공 | 배경 사진 | 사용자가 찾는 정보 |
| 클릭 | 0회 | 여러 번 |
| 읽히는 것 | 요약 한 줄 + 그리드 칩 | 프로젝트·메모·관문 |
| 성공 | 사진이 안 가려진다 | 찾던 것에 도달한다 |

**전제 7의 원칙("배경이 주인공")은 ambient 상태에 대한 원칙이다.** Engaged는 사용자가 명시적으로 진입했으므로 그 순간에는 "보러 온" 것이고, 그때 사진을 덮는 것은 후퇴가 아니다. 전제 8의 anti-reference도 마찬가지다 — **ambient가 일처럼 느껴지면 실패지만, engaged가 일처럼 느껴지는 것은 목적이다.**

대신 계약이 필요하다. Engaged는 (a) 명시적으로 열리고, (b) Esc 한 번으로 닫히고, (c) 닫은 뒤 ambient에 흔적을 남기지 않는다. 이 셋이 지켜지는 한 두 상태는 서로를 오염시키지 않는다.

### "매니저"의 경계 — 어디까지가 이 도구의 일인가

사용자는 "일정조율과 필요한 정보를 제공"이라고 했다. **"일정조율"은 위험 신호다.** 그대로 받으면 자동 스케줄링(Motion·Reclaim 류)으로 가고 범위가 폭발한다.

그런데 이 사용자의 마감은 대부분 **외부가 정한다** — 팀 일정, 릴리즈 창, 배포 승인. 도구에게는 그것을 옮길 권한이 없다. 그러므로 매니저 은유의 정확한 범위는 이렇다.

> **비서는 일정을 대신 잡아주지 않는다. 무엇이 충돌하는지 알려주고 초안을 낸다.**

이 선을 지키면서 값이 나오는 최소 계산은 두 개뿐이고, 둘 다 단순하다.

- **관문 밀집** — 같은 날에 배포 계열 관문이 여럿 몰렸다
- **관문 침범** — 앞 관문의 실제 완료(`doneAt`)가 뒤 관문의 예정일을 넘어섰다

두 계산 모두 자동 이동 없이 **표시와 제안**만 한다. 선행 조사의 "연쇄 이동은 자동이 아니라 제안" 판정이 같은 계약의 다른 얼굴이다.

> **정정(2026-08-21)** — 위 두 계산을 **경고로 만들지 않는다.** 사용자는 여러 프로젝트를
> 병행하며 일정 겹침이 설계상 정상이다. 정상 상태에 대한 경고는 매일 뜨고, 매일 뜨는
> 경고는 경고이기를 멈춘다. **부하 가시화**(이 날에 몇 개가 걸쳐 있다)로 바꾼다.
> 그리고 "마감은 외부가 정하므로 도구에 옮길 권한이 없다"는 절반만 맞았다 —
> 프로젝트 마감은 외부가 정하지만 **개발 세션 마감은 사용자가 조정 가능**하다.

### 검색으로는 닿지 않는 것 — 사용자가 정확히 짚은 지점

사용자의 예: **"어떤 프로젝트인지는 알지만 계정정보를 찾을 때, 계정 ID에 어떤 단어가 들어가는지 알아야 검색을 쓸 수 있다."**

이것은 정보검색에서 오래 알려진 구분이며(Prior Art 참조), 다음 세 가지가 서로 다른 문제라는 뜻이다.

- **어휘를 안다** — "OAuth 리다이렉트"라고 적었던 걸 기억한다. 검색창 한 줄이 최적이다.
- **범주를 안다** — 무엇을 찾는지는 알지만(계정정보) 그 안에 어떤 단어가 있는지 모른다. **검색은 이 경우 아무 도움이 안 된다.**
- **맥락을 안다** — "어제 그거". 최근 목록이 최적이다.

전제 5에 따르면 현재 코드에는 날짜 인덱스 하나뿐이고 텍스트 인덱스도 범주도 없다. 즉 지금 상태에서 메모를 추가하면 **세 경로 중 어느 것도 지원되지 않는다.**

여기서 중요한 관찰 하나. 사용자가 나열한 메모 종류 — 계정정보, 문서 위치, 진행 중 문제, 개발 상세, 배포 기록, 용어정리, 사이트 주소, 서비스 플로우 — 는 **이미 범주 목록이다.** 사용자는 자기 정보의 색인을 이미 알고 있고, windows 메모장이 그것을 담을 자리를 주지 않았을 뿐이다.

### 기존 검색창을 재사용할 수 없는 이유

전제 2에 따라 `SearchManager`는 제출 시 `window.location.href`를 갈아치운다. 이 표면의 정의는 **"웹으로 나가는 문"**이며, 전제 7의 "1초 안에 검색어를 치고 떠난다"가 바로 그 문의 존재 이유다.

여기에 로컬 결과를 섞으면 세 가지가 동시에 깨진다.

- Enter의 의미가 모호해진다 — 구글로 나갈 것인가, 메모를 열 것인가
- 매 타이핑마다 로컬 검색이 돌아 ambient에 계산이 들어온다
- 웹 검색만 하려는 사용자가 자기 업무 메모를 매번 마주친다 (ambient 오염)

## Prior Art

문헌 조사를 수행했다(웹 검색 3회, 2026-08-20). 개요 수준 확인이며 원논문 정독은 하지 않았다.

### 사람은 검색보다 탐색을 쓴다 — 찾는 것을 정확히 알 때조차

Teevan 등의 CHI 2004 연구 [The Perfect Search Engine Is Not Enough: A Study of Orienteering Behavior in Directed Search](http://teevan.org/publications/papers/chi04.pdf)는 이메일·파일·웹에서의 개인 검색 행동을 관찰했다. 결과: **검색 활동의 61%가 키워드 검색을 쓰지 않았다.** 참가자들은 목표를 정확히 알고 있을 때조차 키워드로 점프(teleporting)하지 않고, 맥락 지식을 길잡이 삼아 **작은 단계로 좁혀 갔다**(orienteering).

이유로 지목된 것이 인지적 편안함과 **통제감** — 자기가 어디에 있는지 알면서 이동한다는 감각이다.

이 저장소 맥락에서의 함의는 직설적이다. **검색창 하나만 주는 메모 기능은 사용자 행동의 39%만 지원한다.**

### 위치 기반 탐색이 선호되는 이유는 그것이 "상기시켜 주기" 때문이다

Barreau와 Nardi의 [Finding and Reminding: File Organization from the Desktop](https://homepages.cwi.nl/~steven/sigchi/bulletin/1995.3/barreau.html) (1995)은 데스크톱 파일 조직을 관찰해 네 가지를 보고했다. 사용자는 (1) **상기 기능(reminding function) 때문에** 위치 기반 찾기를 선호하고, (2) 정교한 분류 체계를 피하며, (3) 실제로 보관하는 정보는 적고, (4) 정보를 **일회성·작업중·보관** 세 종류로 다룬다.

이 제품에게 이것은 우연 이상이다. **이 확장의 존재 이유가 이미 "상기(reminder)"다.** 문헌은 탐색과 상기가 별개 기능이 아니라 **같은 행위의 두 얼굴**이라고 말한다. 즉 탐색 표면을 잘 만들면 그것이 곧 리마인더가 되고, 두 상태(ambient/engaged)를 잇는 다리가 된다.

(3)과 (4)도 설계에 직접 들어온다. 보관량이 적다는 것은 정교한 검색 엔진보다 **짧은 목록**이 먼저라는 뜻이고, 세 종류 구분은 선행 조사의 참조형/사건형 분류 및 프로젝트 아카이브 결정과 겹친다.

### 명령 팔레트는 세 경로를 한 표면에 담는 확립된 관용구다

[Command Palette UI 패턴 정리](https://mobbin.com/glossary/command-palette)와 [UX Patterns for Developers](https://uxpatterns.dev/patterns/advanced/command-palette)에 따르면, 잘 만든 팔레트는 **퍼지 매칭 + 최근 사용 항목 상단 배치 + 단축키 힌트**를 함께 갖고, 빈 상태·로딩·오류를 같은 컨테이너 안에서 계획한다. `Cmd+K`는 VSCode·Linear·Slack·Notion을 가로지르는 사실상의 표준이며, 블록·아웃라인 기반 노트 앱은 팔레트를 1급 기능으로 다루고 코드 편집기보다 **더 짧은 단축키**를 쓴다([참고](https://linuru.com/documents/command-palette/)).

빈 입력에서 최근 항목을 보여주는 것이 이 패턴의 표준 동작이라는 점이 중요하다 — 그것이 정확히 Barreau·Nardi의 reminding function이다.

### 배너가 무엇을 세는가 — 기성 도구에는 이 질문이 없었다

- Todoist·Things의 "Today" 카운트는 태스크 단위지만, **그 세계에서는 태스크가 곧 하나의 행동**이다.
- Google Calendar는 이벤트를 센다. 관문 개념이 없다.
- [Linear의 due date](https://linear.app/docs/due-dates)는 이슈당 하나다.
- 반면 CI·배포 파이프라인 UI는 **스테이지 단위**로 표시한다. 관문을 세는 선례는 개발 도구 쪽에 있다.

즉 할 일 도구들이 이 질문을 만난 적이 없는 이유는 그들의 모델에서 "작업 = 행동"이기 때문이다. 관문 모델에서는 **행동 = 관문**이므로 답이 달라질 수 있다.

## Verdict

### 판정 1 — 프로젝트는 사실상 필수다 (선행 판정 1 정정)

- 프로젝트 선택의 **기본값은 "마지막에 사용한 프로젝트"**로 한다. 매번 고르게 하면 입력 마찰이 기록을 막는다
- **Inbox는 남기되 예외로 취급한다** — 목록 맨 아래, 기본 선택 아님. 사용자가 든 예("개발자 세션 준비")가 그 자리다
- 프로젝트가 0개인 첫 실행에는 **온보딩이 필요하다.** 프로젝트 없이는 아무것도 적을 수 없는 모델이므로, 이것이 없으면 첫 사용에서 그대로 막힌다
- 아카이브는 선행 판정대로 처음부터 넣는다. Barreau·Nardi의 "일회성/작업중/보관" 세 구분이 같은 방향을 가리킨다

### 판정 2 — 목표를 두 상태로 명시하고 ~~`PRODUCT.md`를 갱신한다~~

> **정정(2026-08-21)** — 갱신이 아니라 **분리**다. 시계 모드는 가정용(주인공: 사진),
> 캘린더 모드는 업무용(주인공: 리마인드 표면)이라 성공 지표가 서로 다르다. 한 문서에
> 상충하는 두 지표를 넣으면 이후 판단이 "어느 쪽 원칙인가"부터 다툰다. `PRODUCT.md`는
> 시계 모드 문서로 확정하고 캘린더 모드용 문서를 새로 만든다. 아래 "갱신할 내용"은
> **새 문서에 들어갈 내용**으로 읽어야 한다. 후속 조사 판정 1 참조

Ambient / Engaged 구분(Evidence 참조)을 제품 문서에 **명시적으로 적는다.** 지금 `PRODUCT.md`는 ambient만 기술하므로, 메모·탐색 기능은 문서상 근거 없이 원칙 1을 위반하는 것처럼 보인다.

갱신할 내용:

- 원칙 1("배경이 주인공이다")에 **적용 상태를 붙인다** — ambient에 대한 원칙임을 명시
- Engaged 상태의 계약 3줄을 추가: 명시적 진입 · Esc 이탈 · 흔적 없음
- anti-reference를 유지하되 **"ambient가 일처럼 느껴지면 실패"**로 범위를 좁힌다
- 매니저의 경계를 적는다: **제안까지, 결정은 사용자.** 자동 일정 재배치는 하지 않는다

이 갱신 없이 메모 기능을 만들면 이후 모든 설계 판단이 문서와 싸우게 된다.

### 판정 3 — 메모의 "종류(kind)"가 곧 색인이다. 이것이 Q4와 Q6를 동시에 푼다

선행 판정 4는 참조 노트를 **프로젝트당 하나의 긴 문서**로 봤다. 그것은 구조적으로 windows 메모장의 파일 하나와 같다 — 안에서 다시 스크롤해야 한다. **종류 슬롯으로 쪼갠다.**

사용자가 이미 나열한 목록에서 프리셋을 도출한다.

| 종류 | 성격 | 담는 것 |
|---|---|---|
| `계정` | 참조 | 계정정보 |
| `링크` | 참조 | 문서 위치 · 사이트 주소 (둘 다 "어디로 가면 있다") |
| `용어` | 참조 | 용어정리 |
| `플로우` | 참조 | 서비스 플로우 |
| `스펙` | 참조 | 개발할 상세 내용 |
| `이슈` | 사건 | 진행 중 문제사항 |
| `배포` | 사건 | 배포 수정내용·기록 |
| `메모` | 기본값 | 그 외 |

여기서 세 가지가 한꺼번에 풀린다.

- **범주 탐색이 성립한다.** (프로젝트, 종류) 두 좌표면 클릭 2회로 도달한다. 사용자가 든 "계정 ID에 어떤 단어가 들어가는지 몰라도" 문제가 **타이핑 0회로** 해결된다
- **Q4(참조/사건을 묻는가)가 사라진다.** 종류를 고르면 참조/사건이 자동으로 따라온다. 사용자에게 묻는 것은 종류 하나뿐이다. 추론이 남는 자리는 `메모`(기본값) 하나뿐이며, 거기서만 "날짜를 붙이면 사건"이라는 단순 규칙을 쓴다
- **프리셋 고정 결정(답변 1)의 배당금이다.** 짧고 고정된 라벨이라 배지·필터·배너가 전부 성립한다

과잉 구조화 위험은 실재한다 — 8지선다를 매번 하면 기록이 막힌다. 완화: `메모`가 기본 선택이고, **나중에 종류를 바꿀 수 있다.** 분류를 입력 시점의 관문으로 만들지 않는다(Barreau·Nardi의 "정교한 분류 체계를 피한다"와 같은 이유).

### 판정 4 — 재접근 경로는 셋이고, MVP는 그중 검색이 아니다 (선행 판정 4 정정)

| 경로 | 사용자가 아는 것 | 근거 | 형태 |
|---|---|---|---|
| **구조 탐색** | 프로젝트 + 종류 | orienteering 61% | 프로젝트 → 종류 슬롯, 클릭 2회 |
| **최근성** | "어제 그거" | reminding function | 빈 상태의 기본 목록 |
| **검색** | 단어 | teleporting 39% | 입력 시작 시 |

**메모 MVP에는 구조 탐색만 넣는다.** 프로젝트 5개 × 종류 8개면 40슬롯이고, 클릭 2회로 전부 도달한다. 이 규모에서는 검색이 없어도 무너지지 않으며, 문헌은 오히려 구조가 먼저라고 말한다. 선행 판정의 "검색과 같은 릴리즈로만 낸다"는 여기서 완화된다 — **필요한 것은 탐색 수단이었지 검색이 아니었다.**

검색과 최근성은 **하나의 표면**으로 뒤이어 낸다. 명령 팔레트가 그 형태다.

- ~~열기: 전역 단축키(전제 4에 따르면 지금은 없으므로 새로 만든다). ambient에 새 버튼을 추가하지 않는 것이 조건~~
  **정정(2026-08-21)** — 전역 단축키는 MVP에서 제외한다. 새 탭은 포커스가 페이지가 아니라
  **주소창에 있는 상태로 열리므로** 페이지 레벨 키 이벤트가 오지 않는다. 페이지를 한 번
  클릭해야 단축키가 살아나는데, 그 클릭이 이미 진입점 클릭과 같은 비용이다 — 단축키의
  유일한 이점(클릭 0회)이 이 화면에서는 성립하지 않는다. **진입점 하나**(달력 헤더의
  `일정 추가` 옆)로 연다. `Ctrl+F` 가로채기는 backlog. 후속 조사 판정 6 참조
- **빈 입력 = 최근 항목** — 프로젝트 배지 + 종류 + 내용 첫 줄. 이것이 Barreau·Nardi가 말한 상기 기능이고, 사용자가 Q8에서 제안한 "최근에 연 파일 + 내용 일부"와 정확히 같다
- 프로젝트 약칭 접두 입력(`PAY `)으로 범위 좁히기 → 종류 목록
- 문자 입력 = 제목·본문 부분일치. 프로젝트 범위가 잡혀 있으면 그 안에서만
- **기존 웹 검색창과 섞지 않는다** (Evidence 참조). 별도 표면, 별도 단축키

사용자 판단대로 이 표면은 **별도 PRD로 분리할 가치가 있다.** 다만 순서는 메모 뒤이지 메모와 동시가 아니다.

### 판정 5 — 배너는 "각 작업의 다음 미완 관문"만 센다 (선행 판정 2 정밀화)

Q7의 모호함("작업을 세는가 관문을 세는가")은 **집합을 먼저 정하면 사라진다.**

> 배너의 대상은 전체 관문이 아니라, **작업마다 하나씩인 "다음 미완 관문"** 집합이다.

이 규칙 아래에서는 작업당 정확히 1개가 세어지므로 **작업 수 = 관문 수**가 되고, 선행 판정 2와 모순되지 않는다. 동시에 세는 대상이 관문이므로 **무엇을 해야 하는지**까지 말할 수 있다.

여기서 부수적으로 하나가 더 해결된다. 개발완료가 지연됐고 운영배포는 아직 미래인 작업은, 지금 코드라면 둘 다 상태를 갖는다. 하지만 사용자가 손대야 하는 것은 지연된 개발완료 **하나**다. 다음 미완 관문만 보면 미래 관문은 자기 차례가 될 때까지 배너에 나오지 않는다.

문장은 프리셋 라벨을 활용해 행동을 말한다.

- ~~`오늘 · 운영배포 1 · 리뷰 1` / `지연 2`~~
- ~~종류가 **3종 이상이면 축약**한다 — `오늘 4건 · 지연 1건`~~
- 0건이면 노드를 지우는 현재 동작은 유지한다

> **정정(2026-08-21)** — **숫자로는 리마인드가 되지 않는다.** 새 탭을 닫았다 다시 열어도
> "오늘 2건"이면 내용이 반복되므로 습관화가 빨라지고, 곧 배너가 있는지조차 인지되지 않는다.
> 세는 집합("각 작업의 다음 미완 관문")은 유효하지만 렌더하는 것은 **제목**이어야 한다 —
> `오늘 · 정산 API 리팩터링 — 운영배포`. 2건 이상이면 가장 급한 것을 제목까지 내고 나머지는
> `외 N건`. 후속 조사 판정 3 참조

### 판정 6 — 베이스라인은 화면을 갖지 않는다. 결정하는 순간에만 한 줄로 나온다

Q8의 답은 목표 갱신에서 바로 나온다. **Ambient에서는 절대 노출하지 않는다.** 회고 화면도 만들지 않는다 — 그것이 전제 8의 anti-reference에 가장 가까운 물건이다.

대신 variance는 **결정이 내려지는 두 순간에만** 그 자리에서 한 줄로 나온다.

- **관문을 미룰 때** — "이 관문은 이전에도 2일 밀렸습니다." 다음 약속 날짜를 정할 때 유일하게 유용한 정보다
- **작업을 닫을 때** — 상세 뷰의 한 줄

이 형태라면 `revisedDue`(Q2, 위임됨)의 깊이도 정해진다. 위 두 문장을 말하는 데 필요한 것은 **횟수와 누적 일수**뿐이므로, 전체 이력 배열 대신 **`revisedDue` 최신값 + `pushCount` + `pushedDays` 누적** 세 값이면 충분하다. 모델을 키우지 않으면서 "여러 번 밀린 작업"을 구분할 수 있다.

### 판정 7 — 평문 저장을 받아들이되, 새는 곳은 내보내기다

사용자의 위협 모델 판단(답변 5)이 맞다. `chrome.storage.local`은 확장 오리진 전용이고, 로컬 PC가 뚫린 상황이면 다른 credential도 함께 뚫린다. 마스킹·잠금·보기 토글은 실제 위협을 줄이지 않으면서 UI만 무겁게 한다.

**다만 저장소 밖으로 나가는 경로가 둘 있고, 그쪽이 실제 유출 경로다.**

- **내보낸 JSON** — 평문으로 디스크에 남고, 클라우드 백업·메신저 전송으로 이동한다
- **미리보기 모드의 `localStorage`** — 이미 문서에 경고가 있지만 개발자를 향한 것이다

암호화보다 싸고 실제 경로를 막는 조치 하나를 권한다. **내보내기 시 "`계정` 종류 메모 N건이 평문으로 포함됩니다" 고지 한 줄.** AES는 backlog로 둔다.

### 판정 8 — 검증은 하루 단위 정성 판단으로 바꾼다

답변 9가 중요한 사실 하나를 알려준다. **M1은 측정 장치로서 실패했다** — "실무 작업 패턴과 매칭되는 게 거의 없어서 측정 가치가 없었다". 그리고 그 매칭 실패의 정체가 바로 선행 조사가 찾은 두 가지, **프로젝트 부재와 관문 부재**다. 즉 2주를 더 썼어도 같은 결과였을 것이다.

- 전제 9의 "2주 dogfooding" 지표는 **폐기 대상**이다
- 새 기준: **하루치 실제 업무를 넣어보고 (a) 손이 가는가, (b) 어디서 막히는가**를 사용자가 보고한다
- 정량 지표를 새로 만들지 않는다. 단일 사용자·하루 규모에서는 정성 보고가 더 정확하다
- 단, 릴리스마다 **"막힌 지점"을 문서에 누적**한다. 그것이 이 제품의 유일한 실증 데이터가 된다

### 판정 9 — 첨부·그림의 병목은 용량이 아니다

사용자가 우려한 저장 용량은 전제 6에 따라 **이미 문제가 아니다**(`unlimitedStorage` 보유). 진짜 비용은 셋이며, 전부 다른 곳에 있다.

- **단일 키 재직렬화** — 전제 3에 따르면 배경 이미지는 이미 base64로 단일 키 배열에 들어간다. 배경 몇 장은 견디지만 메모 첨부는 개수 규모가 다르다. 첨부는 **IndexedDB(Blob)** 로 가야 한다
- **내보내기 폭발** — 전제 11의 200만자 상한이 먼저 터진다. 첨부는 내보내기에서 분리하거나 별도 형식이 필요하다
- **백업 부재** — 로컬 전용이라 PC가 죽으면 끝이다

> **로그인·서버가 필요해지는 이유는 용량이 아니라 백업과 다기기 동기화다.** 이 구분을 흐리면 "용량 때문에 서버를 붙인다"는 잘못된 전제로 설계가 간다.

그림은 **SVG를 우선**한다 — 래스터 이미지보다 작고, 텍스트라서 검색·diff·내보내기가 전부 그대로 동작한다. MVP는 사용자 결정대로 텍스트만이다.

### 갱신된 순서

1. **`project` 엔티티 + 아카이브 + 첫 실행 온보딩**
2. **저장 키 분리** (`projects` / `tasks` / `notes`)
3. **관문 모델 + 프리셋 + 관문 템플릿**
4. **분할 완료 + variance 3필드** (`revisedDue` / `pushCount` / `pushedDays`)
5. **메모 + 종류 슬롯 (구조 탐색만)** — 검색 없이 성립한다
6. **재접근 표면** (팔레트: 최근 + 검색) — 별도 PRD
7. `PRODUCT.md` 갱신은 1번과 **같은 시점**에 한다 — 뒤로 미루면 이후 판단이 전부 문서와 싸운다

### 추가 제안 — 관문 템플릿

관문을 매번 5개씩 손으로 만들면 입력 비용이 기록을 막는다(선행 조사의 실패 곡선과 같은 원리). **프리셋 조합을 하나 고르면 관문이 한 번에 생성되게 한다.**

- *문구 수정형*: `dev → prod`
- *유지보수형*: `dev → stg → prod`
- *기능개발형*: `dev → review → stg → prod → monitor`

그리고 **모든 관문이 필수가 아니다.** 작업마다 필요한 것만 켠다. 미팅처럼 관문이 없는 일정은 선행 판정 2의 "관문 0개 작업"으로 들어간다.

## Open Questions

- [ ] **전역 단축키를 무엇으로 할 것인가.** 전제 4에 따르면 전역 계층이 없어 새로 만든다. 새 탭은 주소창에서 포커스가 넘어오는 특수한 화면이라, `/`는 검색창 타이핑과 충돌하고 `Ctrl+K`는 브라우저 주소창 단축키와 겹칠 수 있다. 실측이 필요하다
- [ ] **팔레트의 발견성.** ambient에 버튼을 추가하지 않기로 했으므로 단축키를 모르면 기능이 없는 것과 같다. 달력 헤더의 작은 진입점 하나는 허용할 것인가, 아니면 첫 실행 힌트로 충분한가
- [ ] **종류 8개가 맞는 수인가.** `링크`에 문서 위치와 사이트 주소를 합쳤는데, 실사용에서 "사내 위키"와 "운영 콘솔"이 같은 슬롯에 있는 것이 자연스러운지 확인되지 않았다
- [ ] **한 종류에 항목이 많아지면 어떻게 되는가.** `이슈`·`배포`는 사건형이라 계속 쌓인다. 종류 슬롯 안에서 다시 스크롤이 되면 판정 3이 풀려던 문제가 한 계층 아래에서 재발한다. 사건형에는 기간 필터가 필요할 수 있다
- [ ] **관문 밀집·침범 경고를 어디에 표시하는가.** ambient에 내면 배너가 두 줄이 되고, engaged에만 두면 정작 필요한 순간(새 탭을 지나칠 때)에 안 보인다
- [ ] **아카이브된 프로젝트의 메모는 탐색에서 어떻게 다루는가.** 완전히 숨기면 "예전 프로젝트의 계정정보"를 못 찾고, 그대로 두면 아카이브가 무의미해진다
- [ ] **`PRODUCT.md` 갱신의 범위.** 두 상태 구분을 넣으면 "성공은 사진이 몇 퍼센트 보이느냐"라는 단일 성공 지표도 상태별로 갈라야 한다. 그 문장은 이 제품 정체성의 핵심이라 가볍게 고칠 수 없다
- [ ] **첨부의 내보내기 정책.** IndexedDB로 분리하면 현재의 단일 JSON 내보내기로는 첨부가 빠진다. "데이터를 잃지 않는다"는 이 제품의 계약과 정면으로 부딪히므로 확장 착수 전에 답이 필요하다
- [ ] **검색 PRD의 경계.** 팔레트가 메모만 다루는가, 작업·관문·프로젝트·바로가기까지 다루는가. 후자면 사실상 이 확장의 두 번째 주 진입점이 되고 판정 2의 두 상태 구분을 다시 검토해야 한다
