## Evidence

### 지금 캘린더가 실제로 하는 일 (기능 정의)

코드가 말하는 정의는 하나다. **이 위젯은 "일정(event)"이 아니라 "마감일이 있는 할 일(dated todo)"의 목록이다.**

| 축 | 현재 값 |
|---|---|
| 시간 단위 | 날짜(all-day)만. 시:분·타임존 없음 |
| 기간 | `startDate`~`endDate` 범위 1개, 최대 366일 |
| 마감 판정 | **종료일 단일 기준.** 3일짜리 일정의 첫날은 아직 지연이 아니다 |
| 상태 | `overdue` / `today` / `soon`(내일) / 무상태. `done`이면 무상태 |
| 중요도 | `low`/`normal`/`high` 3단. 색이 아니라 칩 두께와 기존 hue의 알파 단계로 표현 |
| 완료 | `done` **boolean 하나** |
| 기록 | `note` 2000자, 이벤트당 1개 |
| 그룹 | **없음** |
| 조회 | 셀 클릭 → 그날에 걸친 이벤트 목록(`startDate <= key <= endDate`). 검색 없음, 필터 없음 |
| 입력 | 간편(패널 인라인 Enter, 단일 날짜) + 상세(모달, 범위·중요도·메모) |
| 요약 | 헤더 한 줄 `오늘 마감 N건 · 지연 M건`. 0건이면 노드 자체를 제거 |
| 상기 | 새 탭을 열었을 때의 시각적 상태 변화가 전부. 알림 없음 |
| 저장 | 단일 키 스냅샷 커밋. 쓰기 실패 시 메모리·DOM 미변경(자동 롤백), 읽기 실패 시 쓰기 잠금 |
| 반출 | JSON 내보내기 / 가져오기(전체 교체) |

즉 **캘린더 쪽 기능 정의는 이미 상당히 단단하다.** 저장 실패 계약, 유일 생성 경로, 왕복 날짜 검증 같은 어려운 부분이 끝나 있다. 비어 있는 것은 표현력 두 가지 — **그룹(프로젝트)** 과 **다단계 마감** — 이며, 둘 다 데이터 모델의 문제이지 UI의 문제가 아니다.

### 고충 1 — 다단계 마감이 표현되지 않는 이유

전제 1과 3에서 바로 따라온다. 작업 하나가 가질 수 있는 마감 후보는 `endDate` 하나뿐이다. 사용자가 말한 "개발완료 → 리뷰 → 스테이징 배포 → 운영 배포 → 모니터링"을 지금 넣으려면 **같은 제목의 이벤트를 5개 만드는 수밖에 없다.** 그 순간 세 가지가 동시에 깨진다.

- **요약이 거짓말을 한다.** 전제 4에 따라 배너는 건수를 센다. 작업 2개가 관문을 5개씩 가지면 "오늘 마감 3건"은 작업 3개가 아니라 관문 3개다. 새 탭을 지나치며 읽는 유일한 숫자가 실제 부담량과 어긋난다.
- **연쇄 이동이 수작업이 된다.** 개발이 이틀 밀리면 뒤따르는 4개를 손으로 옮겨야 한다. 옮기는 비용이 기록하는 이득보다 커지는 순간 사용자는 기록을 멈춘다 — windows 메모장을 안 열게 된 것과 같은 실패 곡선이다.
- **"이 작업의 다음 할 일이 무엇인가"가 사라진다.** 5개 칩이 서로 다른 날짜에 흩어져 있고, 그중 무엇이 지금 나를 기다리는지는 사용자의 머릿속에만 있다.

### 고충 2 — 조기마감·지연·범위축소가 전부 `done: true` 하나로 뭉개진다

전제 1에 따라 완료는 boolean이고 **완료 시각을 기록하는 필드가 없다.** `updatedAt`이 있지만 제목 수정에도 갱신되므로 완료 시각의 진실 원천이 아니다. 그 결과 서로 다른 세 사건이 저장소에서 구분되지 않는다.

- **조기 완료** — 계획보다 일찍 끝났다. 남은 시간을 어디에 쓸지 판단할 근거인데 사라진다.
- **지연 완료** — 며칠 밀렸는지가 사라진다. 지금 코드는 "현재 지연 상태인가"만 알고, 완료되는 순간 그 사실이 소멸한다. 다음 관문을 밀어야 하는지 판단할 근거가 없다.
- **범위를 줄여 완료** — 이건 완료가 아니라 **분할**이다. 미룬 부분이 어디에도 남지 않고, 잘해야 메모 본문 어딘가에 문장으로만 남는다.

여기에 개인 도구 대부분이 저지르는 실수가 하나 더 겹친다. **지연 시 마감일을 새 날짜로 덮어쓰면 "밀렸다"는 사실 자체가 소멸한다.** 화면은 항상 "제때 하고 있음"으로 보이고, 회고할 재료가 남지 않는다.

### 고충 3 — 메모장이 10개를 넘으면 무너지는 진짜 이유

사용자가 적는 것을 나열하면 두 종류로 정확히 갈린다.

- **참조형(reference) — 시간이 없다.** 계정정보, 문서 위치, 사이트 주소, 용어정리, 서비스 플로우. 프로젝트가 살아 있는 동안 계속 유효하고 "오늘"과 무관하다. 필요할 때 **찾는다.** 날짜에 묶으면 오히려 못 찾는다.
- **사건형(journal) — 시간이 있다.** 진행 중 문제사항, 배포 수정내용, 그 시점의 결정. 발생 날짜가 의미를 갖는다. 적을 때는 다시 볼 생각이 없지만 나중에 "그때 왜 그랬지"로 되돌아온다.

**windows 메모장이 무너지는 이유는 탭이 많아서가 아니라, 하나의 파일에 이 둘을 함께 쌓기 때문이다.** 계속 봐야 하는 참조형이, 계속 늘어나는 사건형에 파묻힌다. 그리고 탐색이 선형(탭을 눈으로 스캔)이라 파묻힌 것을 꺼낼 방법이 없다.

여기서 따라오는 결론 하나 — **탐색 수단 없는 메모 기능은 같은 실패를 반복한다.** 탭 대신 목록을 주는 것은 해결이 아니다. 목록도 10개를 넘으면 스캔이다.

### 제약 — 이 제품이 허용하지 않는 해법

전제 10이 해법 공간을 강하게 자른다. 이 확장의 성공 지표는 "사진이 몇 퍼센트 보이느냐"이고, 사용자는 이 화면을 **보러 오지 않는다.** 그래서 다음은 시작부터 제외된다.

- 노트 편집기를 새 탭의 주인공으로 만드는 안(Notion/Obsidian형 워크스페이스)
- 프로젝트별 색상 구분 — hue 하나 원칙과 정면 충돌한다
- 진행률 바·통계 카드·상시 대시보드
- 계획 대비 실제(variance)를 밴드에 상시 노출하는 안

## Prior Art

문헌 조사를 수행했다(웹 검색 4회, 2026-08-20). 1차 소스 정독이 아닌 **개요 수준 확인**이며, 각 제품의 실제 동작은 미검증이다.

### 노트-캘린더 통합의 기성 패턴 세 가지

- **노트가 캘린더를 소유한다** — [NotePlan](https://noteplan.co/use-cases/software-developers)은 캘린더 자체를 노트의 축으로 삼는다("Calendar Driven Note Taking"). [Obsidian TaskNotes](https://github.com/callumalpass/tasknotes)는 작업을 frontmatter가 붙은 **노트 파일**로 저장하고 캘린더·아젠다 뷰를 그 위에 얹는다. 진실 원천은 노트이고 캘린더는 뷰다.
- **노트에서 작업을 추출한다** — [Amplenote의 Task Domains](https://www.amplenote.com/help/using_calendar_task_domains)는 노트와 태그 묶음에서 할 일을 뽑아 캘린더 옆 목록을 채운다. [TaskClone](https://taskclone.com/stop-losing-tasks-sync-notes-with-your-task-app-calendar/)은 같은 노트 안의 항목을 규칙에 따라 서로 다른 프로젝트로 분배한다.
- **작업을 캘린더로 끌어다 놓는다** — Amplenote의 Jot에서 캘린더 이벤트로 전환하는 흐름([문서](https://www.amplenote.com/help/jots_task_to_calendar_event)). 캡처는 무구조로 하고 스케줄링은 나중에 한다.

세 패턴의 공통점이 중요하다. **어느 쪽도 "이벤트에 메모 칸을 하나 붙이는" 형태가 아니다.** 전부 노트와 작업 사이에 **제3의 그룹핑 축**(태그·도메인·폴더·규칙)을 두고 양쪽이 그것을 가리킨다. 반대로 이 저장소의 현재 형태(전제 1)는 정확히 "이벤트에 메모 칸 하나"다.

### 계획 대비 실제 — 이미 해결된 문제, 그러나 다른 동네에서

조기/지연을 다루는 표준 해법은 프로젝트 관리 쪽에 확립돼 있다. **베이스라인(baseline)** — 최초 계획 날짜를 얼려 두고, 실제 날짜를 별도로 기록해 둘의 차이(variance)를 본다([TeamGantt](https://support.teamgantt.com/article/48-baselines/), [Project Plan 365 Tracking Gantt](https://www.projectplan365.com/articles/tracking-gantt/)). 핵심은 **계획을 덮어쓰지 않는 것**이다.

그런데 이 개념은 Gantt 기반 팀 도구에만 있고 — [ClickUp에서는 아직 기능 요청 단계](https://feedback.clickup.com/feature-requests/p/baselines-for-gantt-chart) — **개인용 캘린더·할 일 앱에는 사실상 없다.** 사용자가 "구글 캘린더·노션·플래너로는 해결이 안 된다"고 느끼는 지점의 절반이 여기다. 해법이 없는 게 아니라, 개인 도구의 몸집으로 축소된 형태가 없다.

### 다단계 마감 — 팀 도구에서도 미해결에 가깝다

- [Linear의 due date](https://linear.app/docs/due-dates)는 이슈당 **하나**다. 다중 마감 개념이 없다.
- Jira는 환경별 배포를 릴리즈 워크플로 상태(Awaiting Release / Released to Staging / Released to Production)로 다루지만, 커뮤니티 논의에 따르면 [version 객체가 단순해서 "어느 환경에 배포됐는지"를 추적할 수단이 사실상 없다](https://community.atlassian.com/forums/Jira-questions/Tracking-versions-deployment-status-across-environments/qaq-p/2563984). [Jira Deployments 뷰](https://github.com/atlassian/github-for-jira/blob/332b5ae08042c631fdce6465386a6c338e819d99/docs/deployments.md)는 CI가 배포 이벤트를 밀어 넣어야 채워진다 — **사후 기록**이지 사전 계획이 아니다.
- 즉 팀 도구에서 다단계는 **상태(status)** 로 표현되고, 그 상태들이 각자 자기 **예정일**을 갖지는 않는다. 사용자가 필요로 하는 것("다음 주 화요일 운영 배포를 미리 잡아둔다")은 상태 머신으로 표현되지 않는다.

**정리하면 이 조사의 빈칸은 진짜 빈칸이다.** "관문마다 예정일을 갖는 단일 작업 + 계획 대비 실제 보존 + 프로젝트 단위 참조 메모"를 개인용 상시 표면에서 하는 선례를 찾지 못했다. 다만 이는 **검색으로 찾지 못했다**는 뜻이며 부재의 증명은 아니다.

## Precedent

`.claude/_meta/`는 이번에 처음 만들어졌으므로 이 문서가 첫 항목이다. 상충하는 기존 판정은 없다.

저장소 안의 선례는 캘린더 v2 PRD와 그 계획이다(전제 11).

- **이 조사는 그 PRD의 미해결 Open Question 두 개에 직접 답한다.** "진행도의 정의 — 개별 완료 체크 집계인가, 프로젝트 단위 묶음의 진척인가"와 "메모 저장 한계 — 단일 키에 계속 담을 수 있는가". PRD는 두 질문 모두 "그렇게 되면 데이터 모델에 *프로젝트* 라는 새 개념이 들어가고 범위가 다시 커진다"며 미뤘다. 메모장 요구는 그 미룸을 **더 이상 미룰 수 없게 만든다.**
- **PRD의 M1 논리를 그대로 재사용할 수 있다.** "데이터 모델 2차 변경 — 지금이 가장 싼 시점(저장된 데이터가 거의 없음)." 이 논리는 지금도 유효하며, M1 이후 시간이 지난 만큼 매일 더 비싸지고 있다.
- **PRD의 Risk "요약 배너가 소음이 된다"가 이번 설계의 경계선이다.** 관문을 도입하면 배너 숫자의 의미가 바뀐다(전제 4). 배너를 건드리지 않고 관문을 추가하는 방법은 없다.
- **`source`/`externalId` 예약 필드는 M3(Google Calendar 읽기 전용 연동)를 위한 것이다.** 외부 이벤트는 관문을 갖지 않으므로, 관문 모델은 "관문 0개인 작업"을 1급으로 허용해야 한다. 그러지 않으면 M3에서 모델이 두 갈래로 갈라진다.
- **PRD가 M2로 미룬 `chrome.notifications`는 이 조사의 범위 밖이다.** 다만 관문이 생기면 알림 대상이 "이벤트"가 아니라 "다음 미완 관문"으로 바뀐다는 점만 기록해 둔다.

`.claude/plans/calendar-widget-v2.plan.md`의 Task 순서(데이터 모델 → 레이아웃 → 입력 → 시각 언어)는 이번에도 그대로 유효한 순서다. 선행 문서 중 전제가 무효화된 것은 없다 — **Status 갱신을 제안할 문서는 현재 없다.**

## Verdict

### 판정 1 — 먼저 만들 것은 메모가 아니라 `project`다

메모 기능을 먼저 만들면 **windows 메모장의 실패로 정확히 수렴한다.** 파일이 항목으로 바뀔 뿐 그룹도 탐색도 없기 때문이다(고충 3). Prior Art의 세 패턴이 전부 노트와 작업 사이에 제3의 축을 두고 있다는 점이 같은 방향을 가리킨다.

`project`는 메모 기능의 부속물이 아니라 **캘린더와 메모의 공통 부모**이며, PRD가 미뤄 둔 "진행도의 정의"도 이 엔티티가 생기는 순간 해소된다.

최소 형태:

- `id`, `name`, `abbr`(2~4자 약칭), `archived`(boolean), `createdAt`
- **색을 부여하지 않는다.** 전제 10의 hue 하나 원칙과 충돌한다. 구분은 약칭 배지로 한다
- **아카이브를 처음부터 넣는다.** 끝난 프로젝트가 필터에 계속 남으면 그것이 곧 "탭 10개" 문제의 재발이다
- ~~프로젝트 없는 작업·메모를 허용한다(무소속이 기본값). 강제 분류는 기록 자체를 막는다~~
  **정정(2026-08-20)** — 사용자 답변 3: "유지보수도 특정 프로젝트 단위로 생김. 무소속 작업은
  존재할 수 없음." 프로젝트는 **사실상 필수**이고, 기본값은 무소속이 아니라 **마지막에 사용한
  프로젝트**다. Inbox는 예외로만 남기고, 프로젝트 0개인 첫 실행에는 온보딩이 필요하다.
  후속 조사 판정 1 참조

### 판정 2 — 다단계 마감은 관문(gate) 배열로, 단 화면에는 전부 내보내지 않는다

세 가지 안을 비교했다.

| 안 | 데이터 | 캘린더 표시 | 문제 |
|---|---|---|---|
| A. 이벤트를 여러 개 만든다(현행) | 변경 없음 | 관문마다 칩 | 요약이 관문을 센다. 연쇄 이동이 수작업. 작업 단위가 소멸 |
| B. 상태 머신 + 다음 마감 하나 | `stage` + `nextDue` | 작업당 칩 1개 | **미래 배포일을 미리 못 적는다.** 릴리즈 창은 보통 먼저 정해진다 |
| C. 관문 배열 | `gates: [...]` | 선별해서 칩 | 모델 변경 폭이 가장 크다 |

사용자가 "배포일정을 기록한다"고 말한 이상 **미래 관문이 보여야 하므로 B는 탈락**한다. A는 이미 실패 중이다. **C를 택하되, C의 위험(캘린더가 관문 칩으로 뒤덮임)은 렌더 단계에서 막는다.**

```
Task {
  id, projectId|null, title, priority, done,
  gates: [
    { kind, plannedDue, revisedDue|null, doneAt|null }
  ],
  createdAt, updatedAt, source, externalId
}
```

- **`plannedDue`는 불변이다.** 지연으로 날짜를 바꿀 때는 `revisedDue`에 쓰고 원본을 덮지 않는다. Prior Art의 베이스라인을 관문 단위로 축소한 것이며, 이것이 없으면 "밀렸다"는 사실이 소멸한다.
- **`doneAt`이 조기·지연·정시를 한 필드로 해결한다.** `doneAt - (revisedDue ?? plannedDue)`가 그대로 variance다.
- **작업의 "마감"은 다음 미완 관문의 날짜다.** 그래서 요약 배너는 다시 **작업 수**를 셀 수 있다(전제 4 문제 해소). 배너의 문장은 바뀌지 않는다.
- **그리드에 칩으로 나가는 관문을 제한한다.** 기본값 후보는 (1) 다음 미완 관문, (2) `kind`가 배포 계열이면서 오늘 이후인 관문. 나머지는 상세에서만 본다. 전제 6의 `MAX_CHIPS_PER_CELL = 2`가 이미 있으므로 축약 관용구도 갖춰져 있다.
- **관문 0개인 작업을 1급으로 허용한다.** 그때는 지금의 `endDate` 동작과 동일하게 굴러야 한다 — 이것이 마이그레이션 경로이자 M3 외부 이벤트의 자리다(Precedent).
- 연쇄 이동은 **자동이 아니라 제안**으로 한다. "개발완료가 2일 밀렸습니다. 뒤 관문 3개도 함께 옮길까요?" 자동 이동은 사용자가 의도적으로 겹쳐 둔 일정을 조용히 망가뜨린다.

### 판정 3 — "범위를 줄여 완료"는 완료가 아니라 분할이다

별도 액션이 필요하다. **"남은 것을 새 작업으로 떼어내며 완료"** — 원 작업은 `doneAt`이 찍히고, 미룬 범위는 새 작업으로 나와 같은 `projectId`를 갖는다. 이 액션이 없으면 미룬 범위는 메모 본문의 한 문장으로만 남고 캘린더에서 사라진다.

### 판정 4 — 메모는 한 종류가 아니다. 프로젝트당 참조 노트 1개 + 사건 노트 N개

고충 3의 분류를 그대로 데이터로 옮긴다.

- **참조 노트(project note)** — 프로젝트당 1개, 날짜 없음, 항상 목록 맨 위. 계정정보·문서 위치·용어·URL·서비스 플로우가 여기 산다. 개수가 늘어나지 않으므로 파묻히지 않는다.
- **사건 노트(entry)** — 날짜가 붙고 계속 쌓인다. 선택적으로 작업이나 관문에 연결된다. 문제사항, 배포 수정내용, 그날의 결정.

그리고 **탐색이 이 기능의 성립 조건이다.** ~~한 줄 검색(제목 + 본문)과 프로젝트 필터가 없으면 만들지 않는다~~ — 그것 없이 만들면 탭 10개 문제를 이름만 바꿔 재현한다.

**정정(2026-08-20)** — 성립 조건은 *탐색 수단*이지 *검색*이 아니었다. Teevan 등의 연구에서 개인
검색 행동의 61%가 키워드를 쓰지 않는다(orienteering). 그리고 참조 노트를 프로젝트당 "긴 문서 1개"로
두면 그 안에서 다시 스크롤해야 하므로 windows 메모장의 파일 하나와 구조가 같다. 후속 조사는
**참조 노트를 종류(kind) 슬롯으로 쪼개고**, (프로젝트, 종류) 두 좌표로 클릭 2회에 도달하게 하는
안으로 대체했다. 그 결과 **메모 MVP에서 검색이 빠지고** 재접근 표면(최근 + 검색)은 별도 릴리스로
분리된다. 후속 조사 판정 3·4 참조

표면은 새로 만들지 않는다. 전제 7의 우측 패널에 `할 일 / 메모` 세그먼트를 두어 **읽기**를 붙이고, **편집**은 전제 8의 상세 모달 계열에서 한다. 전제 10의 "새 기능은 켠 사람만 본다"를 지키려면 메모 세그먼트 자체가 설정 토글 뒤에 있어야 한다.

### 판정 5 — 저장 키를 지금 쪼갠다

전제 5에 따라 지금은 메모 한 글자를 고쳐도 배열 전체가 재직렬화된다. 전제 9 덕분에 **용량은 문제가 아니지만 쓰기 비용은 문제다.** 참조 노트는 길고 자주 편집된다.

최소 분리: `projects` / `tasks` / `notes`. 스냅샷 커밋 계약(전제 5의 롤백·잠금 동작)은 키마다 그대로 유지한다 — 이 계약은 이 저장소에서 가장 값비싼 자산이므로 재발명하지 않는다.

### 순서와 그 이유

1. **`project` 엔티티 + 아카이브** — 나머지 전부가 여기 매달린다
2. **저장 키 분리** — 모델이 커지기 전에 해야 싸다
3. **관문(gate) 모델 + 마이그레이션** — 저장된 데이터가 적은 지금이 가장 싼 시점(Precedent). 메모보다 **먼저**인 이유는, 사건 노트의 가치가 "어느 관문에서 생긴 일인가"에 붙을 때 가장 크고 관문이 없으면 다시 날짜에만 붙기 때문이다
4. **분할 완료 액션 + variance 저장** — 저장만 하고 화면에는 아직 꺼내지 않는다
5. ~~**메모(참조 1 + 사건 N) + 검색** — 검색과 같은 릴리즈로만 낸다~~
   → **정정**: **메모(종류 슬롯) — 구조 탐색만.** 재접근 표면(최근 + 검색)은 6번으로 분리한다

### 하지 말아야 할 것

- 메모를 먼저 만들고 나중에 프로젝트를 붙이기 — 실패한 원본으로 수렴한다
- 프로젝트를 색으로 구분하기 — 전제 10 위반
- 지연 시 `plannedDue` 덮어쓰기 — 회고 재료가 소멸한다
- 관문 전부를 그리드 칩으로 내보내기 — 밴드가 대시보드가 된다
- 계획 대비 실제를 밴드에 상시 노출하기 — 전제 10의 anti-reference에 가장 가까운 요소다
- ~~검색 없는 메모 목록을 내보내기~~ → **정정**: **탐색 수단(종류 슬롯) 없는 메모 목록**을 내보내기. 검색 자체는 MVP 요건이 아니다

- [ ] **관문 종류(`kind`)를 고정 목록으로 둘 것인가, 자유 텍스트인가.** 고정이면 실제 워크플로와 어긋날 때 못 쓰고, 자유면 "배포 관문만 미리 보여주기" 같은 규칙이 성립하지 않는다. 프리셋 + 사용자 편집이 절충안이지만 편집 UI 비용이 관문 기능 자체보다 커질 수 있다
- [ ] **`revisedDue`를 몇 번까지 허용하는가.** 배열로 두면 완전한 이력이 남지만 모델이 다시 커진다. 최근 1회만 남기면 "여러 번 밀린 작업"을 구분하지 못한다
- [ ] **프로젝트의 수명.** 상시 유지보수 업무는 프로젝트인가? 무소속 작업(Inbox)을 허용한다고 판정했지만, 무소속이 대부분이 되면 프로젝트 축이 무의미해진다 — 실사용으로만 확인된다
- [ ] **참조/사건 구분을 사용자에게 묻는가, 추론하는가.** "날짜를 붙이면 사건"이라는 자동 규칙이 자연스러워 보이지만, 참조 노트에도 갱신 날짜는 필요하다
- [ ] **계정정보를 평문으로 저장하는 문제.** 전제 12의 미리보기 모드 경고는 개발자를 향한 것이지 실사용자를 향한 것이 아니다. 확장 오리진의 `chrome.storage.local`은 다른 페이지가 읽지 못하지만 내보낸 JSON은 평문이다. 계정정보를 1급 용도로 표방할 것인가, 아니면 "적지 마세요"라고 말할 것인가 — **표방하면 마스킹·잠금 요구가 따라오고 범위가 다시 커진다**
- [ ] **검색 범위.** 메모 본문만인가, 작업 제목과 관문까지인가. 후자면 검색이 사실상 이 위젯의 두 번째 주 진입점이 되고, "지나치며 훑어본다"는 사용 맥락과 다른 성격의 화면이 하나 더 생긴다
- [ ] **요약 배너의 문장을 유지할 수 있는가.** 관문이 생기면 "오늘 마감 2건"이 가리키는 것이 작업인지 관문인지 사용자에게 자명하지 않을 수 있다. 판정 2는 작업 수로 세기를 택했지만 검증되지 않았다
- [ ] **베이스라인 정보를 언제 꺼내는가.** 저장만 하고 안 보여주면 만든 값이 없다. 월 단위 회고 화면이 필요하다면 그것은 새 탭이 아니라 별도 표면이고, 전제 10과 다시 충돌한다
- [ ] **이 조사 전체가 여전히 미검증 가정 위에 있다.** 캘린더 v2 PRD가 명시한 "2주 dogfooding" 측정은 수행되지 않았다. 관문 모델은 그 측정을 대체하지 않는다 — 오히려 관문이 실제로 몇 개나 쓰이는지가 새 측정 항목이다
