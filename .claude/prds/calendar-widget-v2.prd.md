## Problem

새 탭 달력 위젯(M1, 커밋 `6118e87`)은 시계와 9분할 위치 그리드를 공유하는 340×380 소형 카드다. 만든 사람 본인이 업무 마감을 여기에 적어두려 했으나 — 여러 날에 걸친 일정을 등록할 수 없고, 무엇이 급한지 시각적으로 구분되지 않으며, 카드 크기가 "지나치며 훑어본다"는 목적에 필요한 정보를 담지 못한다.

그 결과 마감 확인은 여전히 GCal/Notion에서 이뤄진다. 브라우저 체류 시간이 긴 개발자에게 가장 자연스러운 상기 지점인 새 탭이 비어 있는 셈이다. 방치하면 달력 위젯은 **켜져 있으나 쓰이지 않는 기능**으로 남고, M1에 투입한 설계(마이그레이션·스모크 하네스·내보내기)가 회수되지 않는다.

## Evidence

- **Assumption — 확인된 관찰이나 수치 없음. needs validation via dogfooding (2주 실사용 기록)**
- 배경으로 제시된 사용자 진술 (전부 미검증):
  - "M1 실사용에서 한계가 드러남" — 어떤 장면에서 몇 번 막혔는지는 기록되지 않음
  - "별도 캘린더 프로그램은 추가 메모리를 사용하고, 제한된 디스플레이에서 달력 탭까지 상시로 띄우지 않는다"
  - "소형 위젯이 아니라 캘린더 프로그램 수준의 퀄리티 및 디자인을 원한다"
- 검증 방법: M1 배포 후 2주간 (a) 달력에 실제 등록한 일정 건수, (b) 마감 확인 목적으로 GCal/Notion을 연 횟수, (c) 등록을 포기한 장면을 기록한다. 이 세 값이 없으면 아래 성공 지표는 전부 가설이다.

## Users

- **Primary**: 이 확장을 만든 본인. 브라우저에 상주하는 개발자로 하루에 수십 번 새 탭을 연다. 필요가 발생하는 트리거는 **"탭을 열고 다른 페이지로 이동하기까지의 몇 초"** — 그 짧은 순간에 오늘/급한 마감이 눈에 들어와야 한다. 업무 마감 관리 전용이며 누구와도 공유하지 않는다. GCal/Notion을 이미 쓰고 있으므로 이 달력은 **대체재가 아니라 상기(reminder) 표면**이다.
- **Not for**:
  - 팀·타인과 일정을 공유하려는 사용자 — 로컬 저장만 하며 동기화 계층이 없다
  - 시:분 단위 회의 일정을 관리하려는 사용자 — all-day 범위만 다룬다
  - 새 탭이 조용하기만을 바라는 사용자 — 시계 모드가 기본값으로 남으므로 이들에게는 아무것도 달라지지 않는다

## Hypothesis

We believe **위치 설정 없는 전체 너비 상시 캘린더 + 날짜 범위 일정 + 중요도·마감 색상 + 간편/상세 이중 입력(작업 메모 포함)** 이
**"새 탭을 지나치는 몇 초 안에 급한 일정·금일 일정·진행도를 클릭 없이 인지시키고, 그 작업의 기록까지 한곳에 붙잡아두는 것"** 을
**브라우저에 상주하며 업무 마감을 관리하는 본인** 에게 가능하게 할 것이라 믿는다.

We'll know we're right when **새 탭 진입 시점에 (a) 오늘 마감·지연 항목이 클릭 0회로 읽히고, (b) 여러 날 일정이 날짜별 중복 입력 없이 한 번에 등록되며, (c) 2주 실사용 후 "마감 확인 목적"의 GCal/Notion 열람이 사라진다.**

## Scope

**MVP** — 아래 5개를 **하나의 릴리스로 한꺼번에** 낸다 (사용자 명시 결정: "5개 항목 전부 한 번에"). 하나라도 빠지면 "캘린더 프로그램 수준"이라는 목표가 성립하지 않는다는 판단이다.

1. **위치 설정 제거** — 달력 모드에서는 9분할 position 개념이 사라진다
2. **전체 너비 레이아웃** — 화면 가로 폭을 아우르는 형태
3. **날짜 범위 일정** — 시작일~종료일에 걸친 일정을 한 번에 등록
4. **이중 입력 경로** — 간편(인라인 즉시 입력) + 상세(모달). 상세에는 **작업 메모/기록** 필드가 포함된다
5. **중요도·마감의 시각 언어 + 요약** — 색상 기반 중요도 구분, 마감 임박/초과 상태 표시, 새 탭 상단의 요약 배너("오늘 마감 N건 · 지연 M건")

**제약 (사용자 결정)** — `PRODUCT.md` 원칙 1 "배경이 주인공이다"와 원칙 3 "읽히지 않는 정보는 정보가 아니다"를 **유지한다.** 전체 너비는 취하되 높이와 불투명도를 억제한다. 따라서 정보 밀도는 *전부 보여주기* 가 아니라 **급한 것만 크게 보여주기**(우선순위 기반 축약)로 달성해야 한다.

**Out of scope**

| 항목 | 왜 지금 아닌가 |
|---|---|
| 실제 브라우저 알림 (`chrome.notifications` + 백그라운드 스케줄러) | 사용자가 "가능할 경우 검토"로 유보. 권한 추가와 스토어 심사 재검토를 유발하며, M1 없이 단독으로는 가치를 증명하지 못한다 → M2 |
| Google Calendar 양방향 동기화 | OAuth·host permission이 필요하고 스키마가 재설계 대상이 된다. 기존 결정 유지 → M3 |
| 반복 일정 | 범위 일정과 상호작용이 복잡하고, 마감 관리라는 용도에서 우선순위가 낮다 |
| 시:분 단위 일정 / 타임존 | 용도가 "마감일"이지 "회의 시간"이 아니다. all-day 범위만 다룬다 |
| 주간·일간 뷰 | "지나치며 훑어본다"는 맥락에 과잉 |
| 드래그로 일정 이동·기간 조정 | 입력 경로 2종으로 충분한지 먼저 확인한다 |
| 타인과의 공유·협업 | Primary user가 단일 사용자로 명시됨 |
| 시계 모드의 동작 변경 | 기존 사용자(=기본값)의 화면은 달라지지 않는다 (`PRODUCT.md` 원칙 5) |

## Open Questions

- [ ] **밀도 vs 배경** — "배경 가림 최소화"(사용자 선택)와 "캘린더 프로그램 수준의 퀄리티"(사용자 요구)는 동시에 최대화할 수 없다. 충돌 지점에서 무엇을 버리는가? 우선순위 기반 축약으로 양립 가능한지 프로토타입으로 확인해야 한다
- [ ] **"진행도"의 정의** — 개별 일정의 완료 체크 집계인가, 프로젝트 단위 묶음의 진척인가. 후자라면 데이터 모델에 *프로젝트* 라는 새 개념이 들어가고 범위가 다시 커진다
- [ ] **전체 너비 달력과 검색창의 수직 관계** — 달력이 상단 밴드인가 하단 밴드인가. 검색창의 9분할 위치 설정은 그대로 유지되는가
- [ ] **위치 설정 UI의 비대칭** — 달력 모드를 고르면 위치 그리드를 숨기는가, 비활성화해 남겨두는가. 시계로 되돌렸을 때 이전 위치가 복원되어야 하는가
- [ ] **메모 저장 한계** — 메모 길이 상한과 전체 저장 크기. `chrome.storage.local` 단일 키에 계속 담을 수 있는가, 분리해야 하는가
- [ ] **M2 알림의 권한 비용** — 개인용으로 압축 해제 로드만 한다면 스토어 심사가 무의미하다. 배포 형태가 무엇인지에 따라 M2의 비용 계산이 달라진다
- [ ] **기존 M1 데이터** — 단일 날짜 이벤트가 이미 저장돼 있다면 범위 모델로 어떻게 승격되는가 (시작일=종료일 승격이 자명한지 확인 필요)

## Design Direction

이 PRD는 렌더된 UI 없이 요구사항만 정의한다. 아래는 구현 단계로 넘기는 설계 제약이며, 시각적 수렴은 `/mccp:plan` 이후의 impeccable 루프에서 수행한다.

- **상속할 시각 언어**: 기존 글래스모피즘 토큰(`--bg-secondary-glass`, `backdrop-filter: blur(10px)`, `--border-color`, 반경 10~16px). 새 표면을 만드는 것이 아니라 기존 언어를 넓히는 것이다
- **원칙 유지 (사용자 결정)**: 전체 너비를 쓰되 높이와 불투명도를 억제한다. 밀도는 우선순위 축약으로 얻는다

- **색에만 의존하지 않는다**: 중요도·마감 상태는 색 + 형태(dot/배지/두께)로 이중 부호화
- **모션**: `prefers-reduced-motion: reduce`에서 전환 제거
- **키보드**: 그리드 roving tabindex, 범위 선택도 키보드만으로 가능해야 한다. 상세 모달은 포커스 트랩 + Esc 닫기
