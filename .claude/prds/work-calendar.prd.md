# 업무 캘린더 — 프로젝트 단위 다단계 마감과 기록

> 이 PRD는 `.claude/prds/calendar-widget-v2.prd.md`를 **대체한다**(사용자 결정, 2026-08-21).
> v2의 M2(브라우저 알림)·M3(Google Calendar 연동)는 아래 Out of scope와 M5에서 다시 다뤄진다.

## Problem

여러 프로젝트를 병행하는 개발자에게 "작업이 끝났다"는 시점은 하나가 아니다. 개발 완료, 리뷰, 스테이징 배포, 운영 배포, 모니터링이 각각 자기 날짜를 갖고, **그 경로는 작업마다 다르다** — 전 구간을 도는 작업도, 개발만 하고 끝나는 작업도, hotfix로 스테이징을 건너뛰는 작업도 정상이다.

현재 이 확장의 캘린더는 작업당 마감 날짜를 하나만 갖고 그룹 개념이 없다. 이 구조를 담으려면 같은 제목의 이벤트를 여럿 만들어야 하고, 그러면 하나의 작업이 화면에서 흩어지며 일정이 밀릴 때마다 손으로 여러 개를 옮겨야 한다. **옮기는 비용이 기록의 이득을 넘는 순간 기록이 멈춘다.** 실제로 멈췄다.

같은 사람이 프로젝트별 참조 정보(계정, 문서 위치, 용어, 서비스 플로우)는 별도 메모장에 쌓는데, 항목이 10개를 넘으면 **계속 봐야 하는 참조 메모가 계속 늘어나는 사건 메모에 파묻혀** 찾을 수 없게 된다.

방치하면 캘린더 모드는 켜져 있으나 쓰이지 않는 기능으로 남는다. 마감 확인은 계속 외부 캘린더에서, 기록은 계속 메모장에서 일어나고, 이전 마일스톤에 투입한 설계(마이그레이션·스모크 하네스·내보내기)는 회수되지 않는다.

## Evidence

- **관찰된 실패** — 이전 마일스톤을 실무에 부착하지 못했다. "실무에서 작업하는 패턴과 매칭되는 게 거의 없어서 측정 가치가 없었다"(사용자, 2026-08-20). 계획했던 2주 dogfooding은 수행되지 않았고, **수행할 수 없었다는 사실 자체가 데이터다.**
- **실패한 우회책 둘** — (a) 별도 메모장 프로그램: 따로 떠 있어 손이 안 가고, 항목 10개 이상에서 탭 관리가 불가능하다 (b) 현재 캘린더: 켜져 있으나 마감 확인은 여전히 외부 도구에서 한다
- **코드 증거** (2026-08-21 기준) — 작업당 마감 날짜 1개 · 완료 시각을 남기는 필드 없음(완료는 boolean 하나) · 그룹 필드 없음 · 요약 배너는 건수만 렌더 · 겹침을 막는 로직이 없음(즉 겹침은 이미 정상 상태)
- **기존 도구의 부재** — Linear는 이슈당 due date가 하나다. Jira는 version 객체가 단순해 "어느 환경에 배포됐는지" 추적 수단이 사실상 없다. 계획 대비 실제(베이스라인)는 팀용 Gantt 도구에만 있고 개인용 할 일 앱에는 없다
- **운영 경험** — 고정 문구 배너는 대시보드에서 곧 무시된다(본인의 관리자 대시보드 제작·운영 경험). 반면 입장 목적에 정확히 답하는 단순한 값은 단순해도 집중을 끈다. 습관화·배너 블라인드니스 문헌이 같은 결론을 낸다
- **약점 — 전부 단일 사용자의 자기 보고이고 정량 측정은 0건이다.** 이 PRD는 그 위에 선다. 완화는 지표를 늘리는 것이 아니라 각 마일스톤을 **하루 재현 테스트**로 판정하는 것이다(아래 Success Metrics)
- 근거 조사 3건 — `.claude/_meta/2026-08-20-calendar-notes-integration.md` · `.claude/_meta/2026-08-20-retrieval-and-manager-mode.md` · `.claude/_meta/2026-08-20-calendar-mode-work-goal.md`

## Users

**Primary**: 여러 프로젝트를 동시에 진행하는 IT 개발자 1인(이 확장을 만든 본인).

- 작업은 프로젝트 단위로 생기고 일정과 메모도 프로젝트 단위로 기록된다. **유지보수 업무도 특정 프로젝트에 속한다** — 무소속 작업은 예외적으로만 존재한다
- 작업이 dev/stg/prod를 거치되 **경로가 작업마다 다르다.** 고정 파이프라인이 아니다
- **일정이 겹치는 것이 정상이다.** 여러 작업을 병행하며, 하나의 작업이 월·수에 걸치고 화요일에는 다른 작업을 하는 식으로 **불연속하게** 배치된다
- 프로젝트 수준 마감은 대개 외부(팀·릴리즈 창)가 정하지만, **개발 세션 단위 일정은 본인이 조정한다**
- 필요가 발생하는 트리거는 "새 탭을 열고 다른 페이지로 이동하기까지의 몇 초"다. 그 몇 초 안에 오늘 손댈 것이 눈에 들어와야 한다

**Not for**:

- **시계 모드 사용자** — 캘린더 모드는 별개의 제품 목표를 가지며, 시계 모드의 화면은 이 PRD로 달라지지 않는다
- 팀·타인과 일정을 공유하려는 사용자 — 로컬 저장만 하며 동기화 계층이 없다
- 시:분 단위 회의 일정을 관리하려는 사용자 — all-day 날짜만 다룬다

## Hypothesis

We believe **프로젝트 단위로 묶인 다단계 관문(gate)** 과 **제목이 노출되는 "오늘 줄"** 이
**"새 탭을 지나치는 몇 초 안에 오늘 손댈 작업이 무엇인지 상기시키고, 그 작업의 기록을 한곳에 붙잡아두는 것"** 을
**여러 프로젝트를 병행하는 개발자 본인** 에게 가능하게 할 것이라 믿는다.

We'll know we're right when **하루치 실무를 넣어본 뒤 (a) 오늘 할 일의 제목이 클릭 0회로 읽히고, (b) 마감 확인 목적으로 외부 캘린더·노트 도구를 열지 않으며, (c) 메모장을 여는 이유가 남는다면 그것이 무엇인지 목록으로 나온다.**

(c)는 실패 조건이 아니라 **다음 마일스톤의 입력**이다. 0을 목표로 삼지 않는다.

## Success Metrics

이 제품에는 비교 대상이 없어 절대 기준을 세울 근거가 없다. 그래서 지표를 만드는 대신 **대체 행동의 소멸**을 관찰한다. 물음은 "0이 되었는가"가 아니라 **"무엇이 남았는가"** 이며, 남은 것이 곧 백로그가 된다.

| Metric | Target | How measured |
|---|---|---|
| 오늘 손댈 작업의 **제목**이 클릭 0회로 읽힌다 | 예 | **하루 재현 테스트** — 지난 한 주의 실제 업무를 사후에 입력하고, 그때 필요했던 정보가 지금 화면에서 읽히는지 확인한다. 정답이 이미 존재하므로 비교 대상 부재를 우회한다 |
| 마감 확인 목적의 외부 도구 열람 | 하루 0회 | 수동 집계. **베이스라인 미측정** — 현재 근거는 "여전히 그곳에서 확인한다"는 진술뿐이다 |
| 메모장을 연 **이유** | 목록 (수치 아님) | 열었다면 무엇을 적으려 했는지 기록한다. 남은 항목이 다음 마일스톤의 요구사항이 된다 |
| 작업당 실제로 쓰이는 관문 수 | 관찰값 | 1~2개에 머물면 관문 모델이 과잉이라는 신호다. **이 지표는 가설을 반증할 수 있어야 한다** |

**각 마일스톤의 판정은 하루로 끝낸다.** 2주 dogfooding은 폐기한다 — 이전 마일스톤에서 그 방식은 아무 값도 내지 못했다. 정량 지표를 새로 만들지 않는다. 단일 사용자·하루 규모에서 정량화는 정밀도의 착시만 준다.

## Scope

**MVP = M1 + M2 + M3.** 이 셋이 있어야 "업무 캘린더가 실제로 쓰이는가"라는 가설을 검증할 수 있다. M4~M6은 그 결과로 범위를 다시 정한다.

**마일스톤 경계의 기준은 디자인 검증의 유무다.** M1과 M3은 디자인 수렴(impeccable 루프) 대상이라 반복과 수정이 크고, M2는 데이터 작업이라 그렇지 않다. 이 둘을 한 덩어리로 묶으면 디자인 수렴이 데이터 작업을 인질로 잡는다. 그래서 갈랐다.

**Out of scope**

| 항목 | 왜 지금 아닌가 |
|---|---|
| **전역 단축키** | 새 탭은 포커스가 주소창에 있는 상태로 열려 페이지 키 이벤트가 오지 않는다. 페이지를 한 번 클릭해야 살아나는데 그 클릭이 이미 진입점 클릭과 같은 비용이라, 단축키의 유일한 이점이 이 화면에서는 성립하지 않는다 → backlog |
| **자동 일정 재배치** | 매니저의 경계는 "제안까지, 결정은 사용자"다. 겹침이 정상인 워크플로에서 도구가 일정을 옮기면 의도적으로 겹쳐 둔 배치를 조용히 망가뜨린다 |
| **겹침·밀집 경고** | 겹침이 정상이므로 경고는 매일 뜬다. 매일 뜨는 경고는 경고이기를 멈춘다. 경고 대신 부하를 표시만 한다(M3) |
| **회고·통계 화면** | 계획 대비 실제는 저장하되 화면을 갖지 않는다. 결정을 내리는 순간에만 그 자리에서 한 줄로 나온다 |
| 브라우저 알림 (`chrome.notifications`) | 권한 프로필을 바꾼다. 상시 표면이 먼저 쓰이는지 확인한 뒤에 판단한다 (구 v2 M2) |
| Google Calendar **양방향** 동기화 | OAuth와 host permission을 요구한다. M5의 단방향 내보내기가 값의 절반을 권한 없이 가져오는지 먼저 본다 (구 v2 M3) |
| 사용자 정의 메모 종류 | 종류를 프리셋으로 고정하는 결정을 유지한다. 목록 확장은 코드 상수 수정으로 하고, 사용자 편집 UI는 만들지 않는다 → backlog |
| 저장 데이터 암호화 (AES) | 위협 모델상 로컬 PC가 뚫리면 다른 credential도 함께 뚫린다. 마스킹·잠금·보기 토글은 실제 위협을 줄이지 않는다 → backlog |
| 메모 첨부 · 자유 그림 · 이미지 | MVP는 텍스트로 확정. 저장 방식과 내보내기 정책이 함께 정해져야 한다 → backlog |
| 레이아웃·위젯 모양 전면 설정 | M3은 요약형/월간형 **두 밀도만** 다룬다. 배치까지 여는 설정은 별도 주제다 → backlog |
| 시:분 단위 일정 · 타임존 · 반복 일정 | 용도가 "마감일"이지 "회의 시간"이 아니다 |
| 팀 공유·협업 | Primary user가 단일 사용자다 |

## Design Direction

이 PRD는 렌더된 UI 없이 요구사항만 정의한다. 아래는 구현 단계로 넘기는 설계 제약이며, 시각적 수렴은 `/mccp:plan` 이후의 impeccable 루프에서 수행한다.

**핵심 제약 — 목표는 갈리지만 재료는 상속한다.** 같은 확장에서 나오는 두 모드이므로 패턴이 완전히 바뀌면 이질감이 생긴다(사용자 결정).

| 갈아 끼우는 것 (캘린더 모드 고유) | 상속하는 것 (모드 무관) |
|---|---|
| 주인공 — 배경 사진이 아니라 **리마인드 표면** | 대비 판정 방법 — 토큰 계산이 아니라 **밝은 배경 위에서 렌더된 픽셀 실측** |
| 성공 지표 — "사진이 몇 퍼센트 보이느냐"가 아니라 **"상기되는가"** | 유리 표면의 정당화 조건과 `brightness` 규칙 |
| anti-reference의 적용 범위 — "일처럼 느껴지면 실패"는 **지나치는 상태에만** 적용 | 화면의 hue 계열은 accent 하나 · 상태 색은 발생 시에만 |
| 두 상태(지나침/머무름)의 계약 — 명시적 진입 · Esc 이탈 · 흔적 없음 | 타이포·모션·포커스 링·한국어 줄바꿈(`keep-all` + `overflow-wrap`) |

**M1이 이 갈아 끼우기를 문서로 확정하는 마일스톤이다.** 그전까지 M3의 시각 판단은 근거 문서가 없다.

M3에 걸리는 시각 제약:

- **배너가 제목을 담으면 대비를 다시 재야 한다.** 기존 배너 문구보다 길고 작아질 수 있으며, 밴드 위 텍스트는 이미 실측에서 취약한 자리다
- **부하와 중요도가 같은 시각 축을 쓰면 안 된다.** 중요도가 이미 알파 단계를 쓰고 있으므로, 겹친 개수는 형태(테두리·패턴·개수 표기)로 갈라야 한다
- **요약형/월간형은 같은 데이터의 다른 투영**이며, 설정에서 사용자가 고른다. 자동 전환은 하지 않는다
- 색에만 의존하지 않는다 — 마감 상태와 중요도는 색 + 형태로 이중 부호화한다
- `prefers-reduced-motion: reduce`에서 전환을 제거한다
- 키보드로만 조작 가능해야 한다 — 그리드 roving tabindex, 모달 포커스 트랩과 Esc

M4에 걸리는 제약:

- 상세는 **점진 공개 한 경로**로 만든다(칩 → 팝오버 → 패널/모달). 형태를 사용자 옵션으로 빼지 않는다 — 사용자가 한 명이라 선택지가 값을 만들지 않고, 두 경로는 어느 쪽도 다듬어지지 않는다
- **팝오버는 밴드 안에 렌더할 수 없다.** 밴드에 걸린 `overflow: hidden` 때문에 잘리므로 별도 레이어가 필요하다
- 진입점은 **하나만** 추가한다. 지나치는 상태에 새 버튼을 늘리지 않는다
